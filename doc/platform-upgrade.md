# 平台运行与升级

本文适用于现有平台数据库的增量升级。完整开发说明见[系统开发文档](向量库访问控制系统开发文档.docx)。共享文件服务、模型和存储由对应负责人部署，平台升级不替代这部分联调。

## 确认运行目标

升级前记录当前提交、Java 版本、实际应用数据源、Redis 目标和已有迁移。以正在运行的配置和启动参数为准，不仅查看 Compose 默认值。本轮开发使用过的本机原生数据库与容器默认数据库并非同一实例；不要把容器默认库当作现有业务库。

平台使用 Java 8，文件服务使用 Java 17。前端按锁文件安装依赖，生产构建使用 `npm run build:prod`；本轮使用 Node.js 24.11.1 构建，项目提交钩子使用 Node.js 16.20.2。已验证的版本记录不表示其他版本均已兼容。

`scripts/check-env.sh` 只做入口连接检查。数据库和缓存目标必须显式指定，例如：

```bash
PLATFORM_DB_HOST=127.0.0.1 PLATFORM_DB_PORT=3306 \
PLATFORM_REDIS_HOST=127.0.0.1 PLATFORM_REDIS_PORT=6380 \
bash scripts/check-env.sh
```

上述端口只是示例，必须替换为运行实例的实际连接值。脚本不读取或输出密码，不调用文件列表接口，也不修改服务配置。前后端及文件服务目标可通过 `PLATFORM_FRONTEND_URL`、`PLATFORM_BACKEND_URL`、`PLATFORM_FILE_HOST`、`PLATFORM_FILE_PORT` 覆盖。退出码 0 表示所列入口连接检查通过，1 表示连接或参数失败，2 表示有项目未检查。TCP 连接成功不代表数据库认证、文件解析或知识检索已正常。

## 备份与迁移

先对实际业务库备份并确认备份可恢复，保留上一版服务包、前端产物、配置和提交编号。备份含人员及业务数据，应留在受控位置，不进入 Git 仓库。

既有环境按已执行记录补齐缺失项，不要按文件名顺序遍历执行整个 `sql` 目录。历史脚本含演示数据、菜单重组、权限重设及数据修复，重复执行可能改变业务状态。若无法确认迁移来源，先在隔离副本核对结构与数据。

本轮增量依赖如下：

| 迁移 | 执行前提与检查 |
| --- | --- |
| `add_rag_audit_query_indexes_20261029.sql` | 审计表已存在；检查同名索引定义后执行，验证目标查询使用情况 |
| `add_access_time_scenarios_20261029.sql` | 策略及版本表已完成历史迁移；保留既有同编码策略，不自动创建绑定 |
| `add_group_manager_20261030.sql` | 用户组表已存在；新增可空负责人编号，不指定现有组负责人 |
| `add_governance_export_permissions_20261030.sql` | 访问监控、IP 黑白名单列表菜单各存在且唯一；已有同名导出权限必须属于对应列表菜单 |

执行导出权限迁移前，分别查询 `sys_menu` 中 `system:accessLog:list`、`system:ipBlacklist:list`、`system:ipWhitelist:list`，确认每项仅有一条 `C` 类型菜单；已有对应 `:export` 记录必须是该菜单下启用的 `F` 类型按钮，且不能重复。出现缺失、重复或归属冲突时停止，先修正迁移前提；不要用重复插入或重新分配角色绕过问题。

导出权限迁移可重复执行，不会自动分配角色。超级管理员按现有机制使用；其他管理角色需由有权管理员按岗位需要授予对应导出权限。普通知识门户不因此获得平台管理入口或导出能力。权限变更后按现有登录机制刷新会话，核对最终权限集合。

目前尚未提供经过完整空库安装验证的一键初始化包。`ry_20200920.sql` 是框架基础库，单独导入不能得到完整平台；已有业务库的升级验证不能替代全新安装验证。

## 构建与切换

在平台 Java 8 环境执行：

```bash
mvn -pl ruoyi-admin -am -DskipTests clean package
```

确认成功生成 `ruoyi-admin/target/ruoyi-admin.jar`，再停止旧平台进程并启动新包，避免新旧进程占用同一端口。前端在 `ruoyi-ui` 目录安装锁定依赖并执行生产构建，将生成的 `dist` 发布到实际前端站点。修改 Java 服务后需要重启对应进程，替换源文件不会让已运行的 JAR 自动更新。

本批平台切换不要求重新创建文件服务、MariaDB、Redis、MinIO 或 Milvus，也不要求重建业务数据卷。

## 切换后的核对

核对新服务的启动时间、实际产物和健康入口。只复测受本批影响的行为：

- 策略列表及 Excel 区分可执行、历史、无效和停用状态；历史或无效规则不能新增、重新启用绑定。
- 访问监控、IP 黑白名单按当前筛选导出真正的 `.xlsx`，分页位置不限制导出范围；无结果仍生成表头，超一万条明确拒绝。
- 访问监控导出包含编号、访问时间与拒绝原因；黑白名单包含来源、状态、维护时间和备注。
- 导出须具有对应权限，下载须属于当前账号。普通用户和匿名请求不能读取平台导出。
- 现有用户组、成员、人员安全属性、文档和策略绑定保持原值，角色没有被自动授予新权限。

导出操作本身会记录操作审计，下载文件按现有归属、过期和清理规则管理。旧前端资源缓存应在切换后刷新。

## 回退与交付边界

服务切换失败时，先停新进程，恢复已保留的上一版平台包、前端和配置。新增负责人字段与导出按钮权限属于向后兼容的增量元数据，不应为回退服务而直接删列、删除用户组或重放演示脚本。确需回退数据库时，由数据库负责人依据备份、迁移记录和升级后业务写入制定恢复方案，避免覆盖新业务记录。

本批不会补齐正式语义嵌入、回答服务、OCR 弱版式、内部服务可信调用、向量标签一致性或共享存储恢复。部署后仍需这些服务的联合验证，以及目标环境持续负载和真实异常样本验收。
